# 对话树论文阅读器：需求分析、可行性与产品建议

> 场景：个人精读论文时的 AI 问答。  
> 结论：**技术上完全可行，没有硬门槛。真正的难点不在“画一棵树”，而在两件事：分支之后如何低成本回到原阅读位置；一棵树的上下文如何压缩成模型能用好、用户能看懂的东西。**
>
> **v0.2 交互更新**：主界面已改为“聊天流 + 浮动批注便签”，原“地图 + 阅读器”降级为结构图。树仍然是数据模型，但导航改为左侧树状目录和全屏结构图；选中句子新建的批注便签会连线到原句、可放大/收起，失焦便签变暗但保留。见 `app/public/annotate.*`。

---

## 0. 结论先行

1. **值得做**。现有产品分别解决了“分支”“树可视化”“论文划词解释”中的一两个点，但“句子级锚点 + 森林 + 共享记忆 + 论文工作台”这个组合仍然是空的。
2. **不要做成“把长回答塞进思维导图节点”**。长文本在导图里不可读。推荐“**地图 + 阅读器**”双栏：地图负责结构与导航，阅读器负责长文阅读。
3. **“一棵树之前的所有提问”不能按时间全量拼进上下文**。树是偏序不是全序，兄弟分支会互相污染，成本也会线性膨胀。建议改成“**路径原文 + 树级摘要 + 会话级记忆 + 显式引用**”，并且让用户看得见、能开关。
4. **最高优先级的交互不是“提问”，是“返回”**。用户真正的动作循环是：读 → 卡住 → 问 → 懂 → 回到刚才那段继续读。普通聊天软件只优化了“问”，没有优化“回”。
5. **先做 2 周 P0（无 PDF、无工具）**，用一篇真实论文 dogfood。核心风险是 UI 认知负担，不是技术实现；先用最小版本验证“树是否真的降低了摩擦”，再投入 PDF 和工具。

## 1. 你的诉求，翻译成产品机制

| 你的描述 | 对应的产品机制 | 真正的难点 |
|---|---|---|
| 基于回答的任何句子继续提问 | 句子锚点 anchor：引用文本 + 位置 + 版本 | 锚点漂移、跨段落选择、重新生成后的失效 |
| 以树的结构提问 | 节点 `parent_id`；一个会话是一棵森林 | 长文本节点的可读性、布局稳定性 |
| 单开树根问其它问题 | 同一 session 下多个 root | 树间关系、记忆共享、根的颜色/命名 |
| 树与树上下文互通 | 会话级记忆 + 显式引用 | **不能全量拼接**，否则污染和成本失控 |
| 节点受“到根的路径”影响 | 祖先路径进入 prompt | 深路径的 token 预算、摘要策略 |
| 受“树之前所有提问”影响 | 树级进展摘要（不是原文） | “之前”在树里没有全序 |
| UI 清晰体现树、可展开收起 | 地图 + 阅读器；折叠、路径高亮 | 信息密度与阅读舒适度的平衡 |
| 每个提问有时间，AI 可读 | UTC 存储 + 本地展示 + 紧凑注入 | 注入格式、时区、token 成本 |
| 工具调用、文件上传 | 工具事件 + PDF 工作台 | 分阶段、权限、引用准确性 |

你描述的流程可以抽象成一个循环：

```text
读论文 ──卡住──▶ 提问 ──回答──▶ 局部理解 ──▶ 回到刚才的位置继续读
   ▲                                              │
   └────────────── 又卡住 / 又产生新问题 ◀─────────┘
```

普通聊天软件把这个循环压扁成了一条不断向下滚动的线：你确实能问，但“回到刚才那段”要靠记忆和滚动，分支一多就彻底丢失。**所以这个产品的北极星指标不是“提问数”，而是“从产生疑问到回到原文继续读的时间”。**

## 2. 五个需要修正或补全的点

### 2.1 “树之前的所有提问”不是一个良定义的上下文

一棵树不是一条时间线。假设：

```text
根：这篇论文解决什么问题？
├─ 分支 A：为什么 RNN 不能并行？   ← 你后来发现这条线理解偏了
└─ 分支 B：复杂度为什么是 O(n²)？  ← 三天后在这条线上继续问
```

如果“这棵树之前的所有提问”按创建时间全量拼进去，分支 B 会继承分支 A 里那些你后来推翻的结论。模型不会自动知道“A 是错的”，它只会被上下文带偏。除此之外还有三个问题：

- **成本线性增长**：每个节点都带全树历史，深度越大越贵。
- **注意力稀释**：长上下文里，真正相关的祖先路径反而被淹没。
- **不可解释**：用户不知道模型这次到底看到了什么，出错时无法定位。

**推荐分层：**

| 层 | 内容 | 是否原文 | 默认 |
|---|---|---|---|
| 路径 | 当前节点到根的 Q/A | 原文（超预算才摘要） | 开 |
| 树摘要 | 本树问过什么、已得结论、未决问题 | 压缩 | 开 |
| 会话记忆 | 论文元信息、术语表、用户偏好、置顶结论 | 压缩 | 开 |
| 显式引用 | 用户 `@` 的其它节点/分支/树 | 原文或摘要 | 按需 |
| 语义检索 | 全 session 的相关片段 | 片段 | 可选 |

一条简单的规则：**原文只给“路径”和“当前锚点”，其它一律摘要；所有层对用户可见、可开关。**  
树与树之间共享的是“会话记忆”，而不是彼此的聊天记录。这既满足“同一个会话上下文互通”，又不会让两棵树互相污染。

### 2.2 追问的粒度是“断言”，不是“整条回答”

用户说“对回答里的某个点不懂”，这个“点”通常是一句断言、一个公式、一个术语、一处引用。它不是一个 800 字的回答。所以：

- **锚点是一等公民**：记录 `quote + prefix/suffix + 起止偏移 + 页码/坐标 + 回答版本`。
- **树的边应该带锚点**：从“这句话”长出一个子问题，边上显示被追问的引文；同一句话被追问多次时，子问题分组，不要重复画边。
- **三种分支动作要区分**，不要都塞进一个“回复”按钮：
  1. **继续追问**：针对整条回答，上下文是整条路径；
  2. **就这句追问**：针对选中文本，上下文额外加锚点及所在段落；
  3. **换个回答**：同一个问题的另一个答案变体，是兄弟节点，不是子节点。

锚点的工程细节见 §4.3。这里先说产品结论：**没有锚点，树就只是“消息分支”；有了锚点，树才真正对应“阅读时的困惑结构”。**

### 2.3 真正的摩擦在“返回”，不在“提问”

你原话里最关键的一句是：“这个点搞懂了，我要回到之前的问题回答上继续看，这非常麻烦。”  
这说明产品的高价值动作是：

- 把当前子分支标记为“已理解”；
- 自动收起这个子分支；
- 回到父节点；
- **恢复父节点上次的滚动位置**，让你接着刚才那段读。

这应该是**一个按钮 / 一个快捷键**，而不是“滚动、找、点、再滚”。建议：

- `已理解，收起并返回`：标记 `understood`、折叠子树、选中父节点、恢复阅读位置。
- 每个节点记住自己的 `scrollOffset` 和“最后阅读时间”。
- `Esc` 返回父节点；面包屑可点；地图上始终高亮当前路径。
- 已理解的节点变暗、打勾，但保留在图上，作为“我读过这里”的痕迹。

如果只能做一个差异化功能，我会选这个，而不是更炫的树布局。

### 2.4 纯树不够：思考会汇合

真实阅读不是只分叉不合并。你会：

- 从两个分支得出同一个结论；
- 发现 A 分支的结论能回答 B 分支的问题；
- 想把三个子问题的答案合并成一段小结。

纯树会强迫你复制内容。建议在树之上加一层**弱 DAG**：

- **引用边**（虚线）：节点 A 关联到节点 B，但不改变父子关系；
- **合并节点**：选中 2–3 个节点，让 AI 生成一个“小结”，作为它们共同的后继；
- **跨树引用**：树 2 的某个结论可以挂到树 1 的节点上。

树仍然是主轴，DAG 只是偶尔出现的“横向连接”。不要一上来做完整的图编辑器，那会把 UI 复杂度拉满。

### 2.5 时间不是元数据，是上下文

“每个提问有时间，AI 也可读到提问时间”——这个需求看似小，实际上很有价值：

- “我上周是不是问过类似的问题？”
- “这个结论是三天前得出的，我当时可能漏了一个前提。”
- “这篇论文是 2017 年的，用今天的眼光看，哪些结论已经过时？”
- 复习时按时间回放：“那天晚上我到底想明白了什么？”

实现建议：

- **存储**：UTC ISO 8601 + IANA 时区（`Asia/Shanghai`），不要只存本地字符串。
- **展示**：地图节点显示 `19:38`，hover 显示完整日期；阅读器显示 `2026-10-18 19:38 (GMT+8)`；超过一天显示“3 天前”。
- **注入**：不要给每条消息塞完整 ISO 字符串。用紧凑格式，例如 `用户（19:32 · 3 小时前）`，并在 system 里给一行“当前时间：2026-10-18 19:45，Asia/Shanghai”。需要精确时间时，让模型调用 `timeline.search` 工具，而不是把整条时间线塞进 prompt。
- **语义**：提问时间、回答完成时间、工具调用时间、论文出版时间要分开存。回答“这篇论文发表时 Transformer 还没出现”这类问题，靠的是论文元数据，不是会话时间。

## 3. 推荐形态：地图 + 阅读器

### 3.1 为什么不是纯思维导图，也不是纯聊天

| 形态 | 优点 | 致命问题 |
|---|---|---|
| 纯思维导图 | 结构一眼可见，适合展示分支 | 回答是长文本，节点里读不了；缩放后全是字块 |
| 纯聊天流 | 阅读舒适，实现简单 | 结构完全丢失，分支一多就找不到 |
| 纯大纲树（Roam/Logseq 式） | 紧凑、键盘友好、适合深链 | “地图感”弱，空间关系不明显 |
| **地图 + 阅读器（推荐）** | 结构归结构，阅读归阅读 | 需要双栏联动，屏幕宽度有要求 |

核心原则：**选择不等于导航。** 点一个节点，地图不消失、不跳走，只是右侧阅读器切换内容，当前路径高亮。这样你永远不会“迷路”。

### 3.2 布局

```text
┌──────────────────────────────────┬─────────────────────────────┐
│  会话地图（森林）                 │  阅读器                      │
│                                  │  Transformer 论文精读 › …    │
│  ● 树 1                          │                             │
│  ├─○ 这篇论文解决什么问题？       │  你问 · 19:02                │
│  │  ├─○ 为什么 RNN 难并行？      │  这篇论文到底想解决什么问题？ │
│  │  │  └─○ CNN 的局限？          │                             │
│  │  └─○ 复杂度为什么 O(n²)？      │  AI 回答 · 19:02 · 1.2k tok  │
│  │     ├─○ 为什么除以 √d_k？     │  …… [被追问的句子] ……        │
│  │     └─○ O(n²) 后来怎么缓解？  │                             │
│  ● 树 2                          │  ┌ 上下文 3.2k tokens ▾ ┐    │
│  ├─○ 位置编码为什么用正弦？       │  [继续追问…]  [已理解并返回] │
│  └─○ 外推性具体指什么？           │                             │
└──────────────────────────────────┴─────────────────────────────┘
```

- 地图占 60–65%，阅读器占 35–40%；最小宽度约 1100px。
- 窄屏/手机切换成“专注模式”：只显示当前路径 + 兄弟节点的小徽章，地图收进抽屉。
- 三栏（会话列表 / 地图 / 阅读器）在 13 寸屏上太重，MVP 不做；会话切换放顶部下拉。

### 3.3 地图上的节点

节点不是回答，是**问题卡片**：

```text
┌────────────────────────────┐
│▌ 为什么 RNN 难以并行？       │  ← 自动生成标题，≤18 字
│  19:05 · 2 个追问 · 🔧      │  ← 时间、子节点数、工具标记
└────────────────────────────┘
```

- 宽 180–200px，高 64–72px；标题最多两行。
- 左侧色条标识所属树根；子节点继承色相，但饱和度降低。
- 边：**实线 = 继续追问，虚线 = 就某句追问**；当前路径的边加粗染色，其余降到 40% 透明度。
- 折叠：节点右侧 chevron；折叠后显示 `+3` 徽标和堆叠阴影。
- 缩放分级（LOD）：< 0.6 只显示标题；0.6–1.0 加时间；> 1.0 加一行“一句话结论”。
- 超过 100 个节点加 minimap；超过 300 个节点考虑 Canvas/WebGL 渲染。
- 时间显示在节点右上或 meta 行；hover 显示完整日期。

**为什么地图上不显示完整回答**：回答平均 500–1500 字，节点宽度 200px 时完全不可读；如果为了可读性把节点放大，一棵 30 节点的树就会变成一面墙。地图的职责是“让你看见结构”，阅读的职责交给右侧。

### 3.4 阅读器

- **面包屑**：`树 1 › 这篇论文解决什么 › 为什么 RNN 难并行`，每一级可点。
- **问题块**：显示提问时间、锚点引文（如果有）。
- **回答块**：Markdown + 公式 + 代码 + 引用页码；被追问过的句子有底色和角标。
- **锚点角标**：句尾一个小角标，hover 显示“2 个追问”，点击弹出子问题列表，可直接跳转；不离开当前回答就能看到“这句话引出了什么”。
- **上下文条**：`上下文 3.2k tokens · 5 层 ▾`，点开显示每一层的开关和 token 数。这是建立信任的关键：用户知道 AI 这次看到了什么。
- **输入区**：默认“继续追问”；选中文字后出现“就这句追问”的引文 chip；`Enter` 发送，`Shift+Enter` 换行，`Esc` 返回父节点。
- **动作**：`换个回答`、`已理解，收起并返回`、`提升为会话记忆`、`复制为笔记`。

### 3.5 导航与快捷键

- `↑/↓` 同级节点，`←` 父节点，`→` 第一个子节点，`Enter` 打开，`Space` 折叠/展开。
- `Cmd/Ctrl+K` 命令面板：搜索节点、跳转、折叠全部、导出。
- `Cmd/Ctrl+Enter` 发送。
- 点击地图空白取消选中；拖拽平移；滚轮缩放；`F` 适应画布。
- 打开应用时恢复到“上次阅读的节点 + 滚动位置”，并给一个“继续阅读”的提示。

## 4. 数据模型

### 4.1 核心表

```sql
-- 一个 session = 一篇论文 / 一个主题 = 一片森林
CREATE TABLE sessions (
  id            TEXT PRIMARY KEY,
  title         TEXT NOT NULL,
  paper_id      TEXT,
  created_at    TEXT NOT NULL,          -- ISO 8601 UTC
  updated_at    TEXT NOT NULL,
  settings_json TEXT
);

-- 一个 node = 一次提问 + 一次回答（turn）
CREATE TABLE nodes (
  id             TEXT PRIMARY KEY,
  session_id     TEXT NOT NULL REFERENCES sessions(id),
  tree_id        TEXT NOT NULL,         -- 根节点 id；便于“整棵树”查询
  parent_id      TEXT REFERENCES nodes(id),  -- NULL = 树根
  question       TEXT NOT NULL,
  answer_md      TEXT,
  answer_version INTEGER NOT NULL DEFAULT 1,
  status         TEXT NOT NULL,         -- pending/streaming/done/error/stopped
  model          TEXT,
  created_at     TEXT NOT NULL,
  completed_at   TEXT,
  tz             TEXT NOT NULL,         -- Asia/Shanghai
  anchor_json    TEXT,                  -- 见 4.3
  context_json   TEXT,                  -- 本次实际发送的上下文清单
  usage_json     TEXT,                  -- in/out/cached/cost
  title          TEXT,                  -- 自动生成，≤18 字
  takeaway       TEXT,                  -- 一句话结论
  understood     INTEGER NOT NULL DEFAULT 0,
  collapsed      INTEGER NOT NULL DEFAULT 0,
  scroll_offset  REAL DEFAULT 0,
  variant_of     TEXT REFERENCES nodes(id)  -- “换个回答”产生的变体
);

CREATE INDEX idx_nodes_session ON nodes(session_id);
CREATE INDEX idx_nodes_tree    ON nodes(tree_id);
CREATE INDEX idx_nodes_parent  ON nodes(parent_id);

-- 非树引用：关联、合并、矛盾
CREATE TABLE edges (
  id         TEXT PRIMARY KEY,
  session_id TEXT NOT NULL,
  from_node  TEXT NOT NULL,
  to_node    TEXT NOT NULL,
  kind       TEXT NOT NULL,             -- reference/merge/contradicts
  note       TEXT
);

-- 分层记忆
CREATE TABLE memories (
  id          TEXT PRIMARY KEY,
  session_id  TEXT NOT NULL,
  scope       TEXT NOT NULL,            -- session/tree
  scope_id    TEXT,
  kind        TEXT NOT NULL,            -- summary/glossary/pinned/preference
  content     TEXT NOT NULL,
  token_count INTEGER,
  version     INTEGER NOT NULL DEFAULT 1,
  updated_at  TEXT NOT NULL
);

-- 工具调用是节点内的一等事件，不只是日志
CREATE TABLE tool_calls (
  id          TEXT PRIMARY KEY,
  node_id     TEXT NOT NULL,
  name        TEXT NOT NULL,
  args_json   TEXT,
  result_json TEXT,
  status      TEXT,
  started_at  TEXT,
  finished_at TEXT
);

CREATE TABLE attachments (
  id          TEXT PRIMARY KEY,
  session_id  TEXT NOT NULL,
  kind        TEXT NOT NULL,            -- pdf/image/text
  filename    TEXT,
  sha256      TEXT,
  path        TEXT,
  meta_json   TEXT
);
```

如果你希望一条回答能包含多个 assistant/tool 消息，把 `question/answer_md` 拆到 `messages(node_id, role, content, ord)`，`nodes` 只保留树结构与状态。MVP 用单表更快，工具调用多起来再拆。

### 4.2 为什么 `tree_id` 要冗余

`tree_id = 根节点 id`。这样“取整棵树”“树级摘要”“按树导出”都是一条索引查询，不用递归 CTE。代价是移动子树时要更新整棵子树的 `tree_id`——MVP 不做“移动子树”，所以没问题。

### 4.3 锚点：最容易踩坑的地方

```json
{
  "quote": "recurrence precludes parallelization",
  "prefix": "The fundamental constraint of sequential computation is that ",
  "suffix": " within training examples.",
  "start": 412,
  "end": 451,
  "page": 2,
  "rects": [{"x": 120, "y": 340, "w": 210, "h": 18}],
  "source_node_id": "n1",
  "answer_version": 1
}
```

- **不要只存 offset**。重新渲染、编辑、换模型都会让 offset 失效。存 `quote + prefix/suffix + offset`，渲染时做多级定位：
  1. 在 offset 附近精确匹配；
  2. 全文搜索 quote（归一化空白、引号、连字符）；
  3. 用 prefix/suffix 做模糊匹配；
  4. 都失败 → 显示为“原句已变化”的脚注，允许用户重新锚定。
- **有子节点的回答不可变**。一旦某个句子下面挂了追问，就不要原地重新生成这条回答；`换个回答` 生成一个兄弟变体节点（`variant_of`），UI 用 `v1 / v2` 标签分组。否则子节点的锚点会集体漂移。
- **锚点要记录版本**。子节点绑定 `answer_version`；切换变体时，只显示属于该版本的子节点，或者明确提示“该追问基于旧版本”。
- **跨段落选择**：允许，但存多个 rect，并在阅读器里高亮多个片段；上下文里拼接完整段落，而不是只给碎片。

### 4.4 搜索

- SQLite FTS5 对中文默认分词不友好。用 `tokenize='trigram'` 做子串搜索，或接入 jieba 分词；节点少时 `LIKE` 也够用。
- 搜索结果要显示**路径面包屑**，否则搜到了也定位不到。
- 之后再加 embedding（`sqlite-vec`）做语义检索，用于“语义检索”层。

## 5. 上下文编译器

这是产品的“发动机”。树只是 UI，真正决定回答质量的是每次请求到底带了什么。

### 5.1 分层与预算

以 64k 上下文为例：

| 层 | 内容 | 预算 | 稳定性 |
|---|---|---|---|
| L0 System | 角色、输出格式、引用规则、当前时间 | 0.8k | 高 |
| L1 论文 | 元数据 + 全文/章节；单篇论文直接全文，多篇才 RAG | 12k | 高 |
| L2 会话记忆 | 用户目标、背景、术语表、置顶结论、偏好 | 1k | 中 |
| L3 树摘要 | 本树已探索问题、结论、未决点 | 0.6k | 中 |
| L4 路径 | 根 → 父节点的 Q/A；超预算时从最老的开始摘要 | 8k | 中 |
| L5 锚点 | 选中句 + 所在段落/页 | 1k | 低 |
| L6 当前问题 | 用户输入 | 0.5k | 低 |
| 预留输出 | | 4k | |

原则：

- **永远不裁剪 L0 和 L6**；先裁检索片段（若启用），再从最老的路径开始摘要，最后才动 L3。
- **路径摘要不是逐条压缩，而是“已确认结论”列表**：`- RNN 不能并行是因为 h_t 依赖 h_{t-1}`。模型需要的是结论，不是逐字复述。
- **树摘要由异步任务生成**，不要阻塞回答；每次回答完成后用便宜模型更新，带版本号。
- **上下文清单落库**（`context_json`），支持“为什么这么答”的回放。这对调试和信任都很重要。

### 5.2 组装顺序与缓存

树的天然优势是**前缀共享**：同一棵树的多个分支，根到分叉点的 prompt 完全一样。利用 provider 的 prefix caching 可以大幅省钱、降延迟。

推荐顺序（稳定 → 动态）：

```text
[静态规则] → [论文全文] → [会话记忆] → [树摘要] → [当前时间] → [祖先路径] → [锚点段落] → [当前问题]
```

注意：**不要把每次都变的“当前时间”放在最前面**，否则它后面所有内容都无法命中前缀缓存。把时间放到稳定块之后，或者按 5 分钟粒度取整。

- Anthropic：显式 `cache_control` 断点，最多 4 个，适合把“规则 + 论文”钉住。
- OpenAI / DeepSeek：自动前缀缓存，顺序正确才有命中；在 `usage` 里记录 `cached_tokens`。
- 同一棵树的分支尽量复用同一段路径序列化结果，不要在每个分支里重新措辞。

### 5.3 伪代码

```ts
async function buildContext(node: Node): Promise<Prompt> {
  const path = ancestors(node);                 // root → parent
  const budget = model.contextWindow - OUTPUT_RESERVE;

  const layers = [
    staticRules(),                              // L0
    paperCorpus(node.session),                  // L1
    sessionMemory(node.session),                // L2
    treeMemory(node.treeId),                    // L3
    nowLine(),                                  // 动态但很短
    pathLayer(path, budget.path),               // L4
    anchorLayer(node.anchor),                   // L5
    retrievalLayer(node, budget.retrieval),     // L5 optional
    currentQuestion(node)                       // L6
  ];

  return fit(layers, budget, {
    dropOrder: ["retrieval", "oldestPathTurns", "treeMemory"],
    neverDrop: ["staticRules", "currentQuestion", "anchor"]
  });
}
```

### 5.4 Prompt 模板

下面是按**可读性**排列的模板；实际序列化时按 §5.2 的顺序，把论文、会话记忆等稳定块前置，`当前时间` 后置，以保住前缀缓存。

```text
你是论文精读助手。当前时间：2026-10-18 19:45（Asia/Shanghai）。
用户在精读《Attention Is All You Need》（Vaswani et al., 2017）。

【会话记忆】
- 用户背景：……
- 已确认结论：……
- 术语表：……

【本树进展】
- 已探索：……
- 已结论：……
- 未决：……

【论文原文】
<p.2> ……
<p.3> ……

【对话路径】
用户（19:02）：这篇论文到底想解决什么问题？
助手（19:02）：……
用户（19:05）：为什么 RNN 难以并行？
助手（19:05）：……

【当前锚点】
用户选中了上一轮回答中的：「recurrence precludes parallelization」
所在段落：「……」
页码：p.2

【当前问题】
……

要求：
1. 先直接回答，再展开；不要复述路径里已经确认过的内容。
2. 严格区分“论文原话”“你的推断”“外部知识”；引用论文时给页码。
3. 如果锚点或原文不足以回答，先指出缺什么，不要编造。
4. 回答控制在 400 字以内，除非用户要求展开。
```

最后一条很重要：**树里的回答应该短**。长的综述适合单独生成“小结节点”，而不是每个分支都写 1500 字。回答越短，树越可读，追问越聚焦。

## 6. 技术选型

### 6.1 三种形态

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| 本地 Web：Vite + Hono + SQLite | 迭代最快、浏览器直接调试、易加 PDF.js | 需要起一个本地服务；API key 在本地 | **v1 推荐** |
| Tauri 2 + React + SQLite | 单机 App、离线、系统钥匙串、分发简单 | 打包/升级/调试成本更高 | v1.5 再包 |
| Next.js + Postgres | 多设备、分享、协作 | 重、隐私与成本、登录体系 | 以后再说 |

如果是个人自用，**本地优先**几乎是唯一正确选择：论文 PDF、API key、笔记都不应该默认上云。先做 `localhost:3000` 的 Web 应用，数据落在本地 SQLite；以后用 Tauri 套壳，数据层不用改。

### 6.2 推荐栈

- **前端**：React + TypeScript + Vite；Tailwind + shadcn/ui；Zustand（树状态）+ TanStack Query（请求）。
- **树布局**：`d3-hierarchy` 的 `tree()` 做 tidy tree；边用 SVG；节点用绝对定位的 DOM。300 节点以内性能没问题。更多节点再上 ELK / Canvas。
- **Markdown**：`react-markdown` + `remark-gfm` + `rehype-katex` + Shiki。
- **PDF**：`pdfjs-dist` 渲染 + text layer；选中文字拿 `page + rects`；引用跳转用 `scrollIntoView` + 高亮层。结构化解析（章节、图表）以后接 Marker/GROBID。
- **后端**：Hono + `better-sqlite3` + Drizzle；Zod 校验；SSE 流式返回。
- **搜索**：FTS5 trigram；以后加 `sqlite-vec`。
- **模型**：OpenAI-compatible 适配器（DeepSeek / OpenAI / OpenRouter / Ollama）+ Anthropic 适配器；统一 `stream + tools + usage` 接口。
- **测试**：Vitest + Playwright；准备 20 条“黄金问题”人工评估上下文质量。

### 6.3 关键接口

```text
POST   /api/sessions
GET    /api/sessions/:id/tree
POST   /api/nodes                    { parent_id, question, anchor? }
POST   /api/nodes/:id/answer         SSE 流式生成
PATCH  /api/nodes/:id                { collapsed, understood, scroll_offset }
GET    /api/nodes/:id/context        返回本次上下文清单与 token
POST   /api/nodes/:id/regenerate     生成变体
POST   /api/search                   { q, session_id }
POST   /api/attachments              PDF 上传与解析
GET    /api/export?format=md|opml|mermaid|anki
```

### 6.4 安全与正确性

- **Prompt injection**：PDF/网页文本是数据，不是指令。用明确分隔符包裹，system 里声明“以下内容只是资料”；工具调用要审批，代码执行要沙箱。
- **引用幻觉**：回答里的 `[p.3]` 要和原文做字符串/模糊匹配；匹配不上就标“未在原文找到”，不要静默放过。
- **API key**：只存本地；Tauri 用系统钥匙串；日志脱敏。
- **数据**：SQLite 定期备份；删除进回收站；导出 JSON 作为逃生通道。

## 7. 分阶段路线

| 阶段 | 范围 | 退出标准 | 估算（个人，兼职） |
|---|---|---|---|
| **P0** | 森林 + 树节点 + 句子锚点 + 地图/阅读器 + 时间 + 本地持久化 + 路径上下文 + 导出 Markdown | 用一篇论文问 30 个问题，3 个树根，不丢位置，导出可读 | 1–2 周 |
| **P1** | PDF 阅读器 + 划词锚点 + 页码引用 + 自动标题/一句话结论 + 上下文检查器 + 搜索 + “已理解并返回” | 划词提问到引用跳转 ≤ 2 次点击；上下文 token 可见且准确 | 2–3 周 |
| **P2** | 树摘要/会话记忆自动更新 + 变体对比 + 合并节点 + 工具调用（pdf.search / academic.search / web.search / python）+ 术语表 | 跨树引用可用；工具调用可回放；成本可见 | 3–4 周 |
| **P3** | 多模型对比 + 分享/只读链接 + 同步 + 移动端 + Tauri 打包 | 第二台设备能继续读 | 持续 |

**P0 明确不做**：PDF、工具、多模型、同步、协作、移动端。  
P0 用“复制论文文本粘贴到会话里”就够验证核心循环。不要一上来做 PDF，PDF 的解析、坐标、缩放、引用跳转会吃掉你一半时间，而它验证不了“树是否有用”。

> 如果论文精读是主场景、且你希望答案直接带权威引用，**学术检索与交叉验证应提前到 P1**，不要等到 P2。具体工具设计见 [research-tools-design.md](research-tools-design.md)。
>
> 第一版（`app/`）已经把 DeepSeek Search/Fetch + 学术 API 作为 M1 提前实现；PDF 与严格 NLI 交叉验证仍未做，见 [app/README.md](../app/README.md)。

P0 的验收指标：

- 从产生疑问到回到原段落：**≤ 5 秒，≤ 2 次点击**。
- 30 个问题后，树仍然可读（节点标题能区分，折叠后能定位）。
- 导出 Markdown 后，别人能看懂你的阅读路径。

## 9. 体验增强清单（按 ROI 排序）

| # | 功能 | 价值 | 成本 |
|---|---|---|---|
| 1 | **已理解 → 收起并返回 + 恢复滚动位置** | 直接解决“回不去” | 低 |
| 2 | **自动标题 + 一句话结论** | 树可读的前提 | 低 |
| 3 | **锚点角标 + hover 预览子问题** | 不离开回答就能看到分支 | 中 |
| 4 | **追问建议（ghost nodes）** | 解决“不知道问什么”，树自然生长 | 低 |
| 5 | **阅读位置记忆 / 继续阅读** | 长会话必需 | 低 |
| 6 | **上下文检查器（分层开关 + token）** | 建立信任，便于调参 | 中 |
| 7 | **分支对比 / 合并为小结** | 处理“两条路都走了” | 中 |
| 8 | **术语表 + hover 释义** | 论文精读高频需求 | 中 |
| 9 | **引用校验 + 页码跳转** | 防止幻觉，论文场景刚需 | 中 |
| 10 | **导出 Anki / Markdown / OPML / Mermaid** | 把会话变成学习资产 | 低 |
| 11 | **时间线回放** | 复习“我是怎么想明白的” | 中 |
| 12 | **成本/缓存仪表** | 长会话不心疼 | 低 |
| 13 | **命令面板 + 全键盘** | 高频用户效率 | 低 |
| 14 | **只读分享链接** | 把阅读路径发给别人 | 中 |
| 15 | **移动端只读 + 快速追问** | 通勤复习 | 高 |

几个值得展开的：

- **自动标题**：用便宜模型把问题压成 ≤18 字，同时生成一句“结论”。没有它，地图上全是“为什么…？”“那…呢？”，三天后你自己都分不清。
- **Ghost nodes**：在当前节点下方浮出 3 个建议追问，点击才变成真实节点。它降低了“面对空白输入框”的阻力，又不会污染树。
- **提升为会话记忆**：任何节点都可以“置顶”为会话记忆（L2），于是树 2 在提问时能读到树 1 的结论。这比自动共享全部聊天记录更可控。
- **导出 Anki**：论文精读的 Q/A 天然适合做成卡片；导出时保留锚点引文和页码，复习时能回到原文。

## 10. 竞品扫描

| 产品 | 做了什么 | 缺什么 |
|---|---|---|
| [LobeChat](https://lobehub.com/ar/changelog/2024-11-27-forkable-chat) | 可从任意消息创建分支，支持“带上下文/独立”两种模式 | 分支在侧边栏里切换，不是地图；没有句子级锚点；没有论文工作台 |
| [ChatTree](https://chromewebstore.google.com/detail/chattree-tree-view-for-ch/nolkaoiajehpjejljfdkkmochigadiph) | 把 ChatGPT 会话可视化成树 | 只是可视化，依赖 ChatGPT DOM；不能自己组织森林/记忆 |
| [llm-canvas](https://github.com/LittleLittleCloud/llm-canvas) | 用无限画布可视化 LLM 对话流 | 通用工具，不解决论文阅读、锚点、会话记忆 |
| [SciSpace Copilot](https://ojs.aaai.org/index.php/AAAI/article/download/30578/32740) / Explainpaper | 在论文里划词解释、基于选中文本提问 | 线性聊天，没有树；追问多了就丢失结构 |
| Heptabase / Tana / Roam / Logseq / Gingko | 卡片、块引用、树状笔记 | AI 问答与上下文组装不是核心；需要手动维护结构 |
| NotebookLM | 基于资料源的问答与摘要 | 没有分支/森林；阅读路径不可见 |

**结论**：单点能力都有人做，但组合没有：

```text
句子级锚点  ×  森林（多树根）  ×  会话级共享记忆  ×  思维导图式导航  ×  时间上下文  ×  论文 PDF 工作台
```

护城河不是“画树”（这是已解决的问题），而是：

1. **数据模型**：锚点、版本、森林、记忆分层；
2. **上下文编译器**：让每个节点只看到该看的东西，且可解释；
3. **阅读工作流**：划词、引用、返回、复习、导出，形成闭环。

## 11. 我的建议

### 先做 P0，用一个真实论文 dogfood

不要先做 PDF、工具、多模型。先用“粘贴论文全文 + 树 + 锚点 + 返回”跑一周，记录四个指标：

- **返回时间**：从“我懂了”到“回到原段落”的秒数；
- **分支复活率**：一周后还会回看的节点比例；
- **每篇论文的节点数**：10 个还是 100 个，决定性能与 UI 密度；
- **每次回答的上下文 token**：决定成本模型。

如果一周后你发现自己确实在用它，再投入 PDF。如果发现自己还是回到普通聊天窗口，说明问题不在“树”，而在别的地方（比如回答太长、锚点不准、返回不够快），这时候加 PDF 也救不了。

### 三个“不要”

1. **不要把完整回答放进地图节点**。地图是导航，不是阅读器。
2. **不要把兄弟分支的原文自动拼进上下文**。用摘要 + 显式引用；否则树越大，回答越差。
3. **不要在 P0 做协作/同步/移动端**。这些都是乘法项，但前提是核心循环成立。

### 下一步

可以按这个顺序推进：

1. 用这个仓库里的 [prototype/tree-chat.html](../prototype/tree-chat.html) 原型试手感（纯前端假数据，重点看地图 + 阅读器 + 锚点 + 返回）；静态截图见 [prototype/screenshot.png](../prototype/screenshot.png)。
2. 确定三个决策：本地 Web 还是 Tauri；用哪家模型（DeepSeek/OpenAI/Claude/本地）；是否单用户。
3. 搭 P0：SQLite + 树 CRUD + 流式回答 + 地图布局 + 导出。
4. 用一篇你真正要读的论文跑一周，再决定 P1。
